# Business automation

## Registration

1. Validate identity, password and explicit consent; normalize the email.
2. Transactionally create CLIENT and a NEW registration lead.
3. Store a hashed verification token and a durable email outbox record.
4. Create the welcome notification and an audit event.
5. Issue an opaque session cookie. Client confirmation is required before booking or purchase only when the email policy requires it. By default it is optional without a configured HTTP sender; the owner may set REQUIRE_EMAIL_VERIFICATION=true or false. The unverified state is retained, and administrator bootstrap still requires actual verification.

For production, transactional email is attempted immediately through the configured HTTP provider. Unsuccessful delivery remains in the outbox. For localhost, the message and its actual token link are visible at `/api/dev/mailbox`; this route is inaccessible from public hosts. Email links expire in 24 hours; password reset links expire in one hour.

## Payment activation

An authenticated verified client creates an order from a server-priced tariff. LiqPay checkout uses a signed form POST. The provider sends a signed callback to `/api/payments/webhook`. The server validates the signature and exact order metadata, then transactionally inserts a payment, marks the order paid, creates one membership, marks the registration lead WON, and queues email and in-app confirmation. A linked Telegram account also receives a confirmation. Orders and memberships generated by a loopback test payment carry `isDemo: true` and are visibly marked as tests.

Closing or reloading the checkout page cannot manufacture an activation. Repeated provider callbacks are idempotent. Refund status `reversed` cancels the corresponding membership. Pending bank states leave the order pending.

## Scheduled processing

The Worker has a `scheduled()` handler and a fifteen-minute cron trigger in `vite.config.ts`. Deployment must retain that trigger in the generated Worker configuration. Each run:

- Recovers outbox claims older than ten minutes.
- Expires memberships whose end date has passed.
- Sends deduplicated three-day membership expiry reminders.
- Sends deduplicated reminders for classes beginning within two hours.
- Removes expired sessions, tokens and rate limit buckets.
- Sends up to thirty outbox messages.

Email/Telegram reminder preferences are read from the client profile. Authentication and financial confirmations are transactional messages. Outbox entries without a configured provider remain pending. Network/provider failures retry five times, then remain in failed status with a non-secret error. Staff can inspect delivery state in the admin snapshot. Retrying failed messages requires operational intervention; an automatic infinite retry is intentionally absent.

An ADMIN can run processing via `POST /api/admin/automation/run`. An external scheduler can invoke `POST /api/automation/cron` with `Authorization: Bearer <CRON_SECRET>`. Keep the secret out of URLs and logs.

## Telegram

Create a bot using BotFather, then set its username, token and webhook secret as Worker secrets. Register an HTTPS webhook using Telegram's `setWebhook` method, the URL `/api/telegram/webhook`, and the `secret_token` field. The receiver checks `X-Telegram-Bot-Api-Secret-Token` and accepts private chats only.

The authenticated cabinet requests `POST /api/telegram/link`. The server creates a one-use token valid for ten minutes, and returns a `t.me` link. Opening it and sending `/start <token>` securely associates that private chat with the client. Chat IDs cannot be assigned through the public profile API.

Commands implemented: `/profile`, `/membership`, `/schedule`, `/workouts`, `/unlink`, `/help`. Responses are queued durably. Provider update IDs and response event keys prevent duplicate responses. The bot can inspect and remind; booking cancellation and payment inside Telegram are not implemented. No configured token means no outbound calls and a clear unavailable response in the cabinet.

## CRM and staff

Contact forms create NEW leads and confirmation emails. Staff can move leads through NEW, CONTACTED, QUALIFIED, PROPOSAL, WON and LOST, and append immutable author-attributed notes. Support replies notify the client and appear in their ticket history. Catalog edits, role changes, sales and booking mutations produce audit records. Admin snapshots reconnect over SSE for fresh data. CSV export supports clients, leads and orders.
